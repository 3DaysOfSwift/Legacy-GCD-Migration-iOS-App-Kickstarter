Architecture readability review

An app is a company asset. Readability makes it the best one.

Kickstarter's open-source iOS app, before and after migration to the Cooperative Feature Architecture (CFA). We measured what a developer sees when they first open the Xcode project: how many parts it has, where each lives, which vocabulary they need, and how much of it is plain Swift. CFA also gives the app a Model the team can draw on a whiteboard, and a test suite shaped like that drawing.

The headline

A shipping app earns money for as long as people can change it with confidence. After the CFA migration, an engineer of any background can open the project and get a gentle, accurate picture of how many parts it has and where each one lives, using only standard Swift and Apple's own frameworks. The app now has an explicit Model (Features plus services) that fits on a whiteboard, and tests that are easy to find, catalogue and organise.

How to read this report

Every figure is counted or quoted from the two commits above. Where line counts appear they are shown as they are: some traced paths are slightly longer after migration, because plain sequential Swift spells out what an operator graph used to imply. The gain is not fewer lines. It is clarity, idiom, predictability and standard vocabulary: code that a new hire reads the way Apple's documentation reads.

3. A model you can draw on a whiteboard, and a test suite you can map

A team can sketch the whole app from that, and the same drawing tells them where every kind of test belongs. Before, the equivalent Model was spread inside 165 ViewModels, so there was nothing to draw and nothing to map tests against.

What this means for the team

Everyone can hold the same picture: View, ViewModel, Feature, service. A new engineer can ask "where is the test for X?" and find the answer by following the Feature name. A lead can print the table above, see which Features are lightly tested, and plan the next tests. Because each Feature is tested as a unit, a missing test shows up as a thin row, not as a hole nobody notices. (These are reasoned implications; this review did not measure defect rates.)

  internal func requestSearch(parameters: DiscoveryParams) -> Task<Void, Never> {
    if self.parameters?.hasSameSearchInputs(as: parameters) == true,
       let request = self.request, request.cursor == nil {
      return request.task
    }
    self.cancelSearch()
    self.parameters = parameters
    self.nextCursor = nil
    self.completedPageCount = 0
    self.projects = []
    self.emit(.results([]))

    self.hasRequested = true
    return self.requestPage(parameters: parameters, cursor: nil, debounce: debounce)

After · CFALogin: the same behaviour as ordinary Swift
Kickstarter-iOS/1 - View/Views/Login/Controller/LoginViewModel.swift · lines 49-74
  private func submit() {
    AppEnvironment.current.ksrAnalytics.trackLoginSubmitButtonClicked()
    guard let email = self.email, let password = self.password else { return }
    self.loginTask?.cancel()
    let version = UUID()
    self.loginVersion = version
    let feature = self.authenticationFeature
    self.loginTask = Task { [weak self] in
      do {
        let result = try await feature.authenticate(.email(email, password: password))
        guard !Task.isCancelled, let self, self.loginVersion == version else { return }
        self.onLogin?(result)
      } catch {
        guard !Task.isCancelled, let self, self.loginVersion == version else { return }
        if let error = error as? ErrorEnvelope, error.ksrCode == .TfaRequired {
          if let currentEmail = self.email, let currentPassword = self.password {
            self.onTwoFactor?(currentEmail, currentPassword)
          }
        } else if let error = error as? ErrorEnvelope {
          self.onError?(error.errorMessages.first ?? Strings.login_errors_unable_to_log_in())
        } else {
          self.onError?(Strings.login_errors_unable_to_log_in())
        }
      }
    }
  }

5. A typical ViewModel's surface

11. What this means for the company

The measurements above are facts about the code. The points below are what they imply for hiring and risk. They are reasoned consequences, not measured outcomes.

Hiring

A wider pool of candidates can contribute sooner

Swift Concurrency and Observation are part of Apple's own SDK, documented by Apple and taught to every iOS developer. ReactiveSwift is a niche, third-party skill. A codebase written in the standard vocabulary means a hire does not have to arrive already fluent in reactive programming, or spend their first months learning an in-house operator dialect.

Beyond reactive specialists

No longer limited to one kind of developer

Before the migration, reactive vocabulary appeared in about 46% of the app's files. A reviewer who has never used ReactiveSwift could not fully follow the project page, login or search. After, an engineer from any background (UIKit, SwiftUI, or a different platform) can read the same screens, because the screens are built from constructs they already know.

Longevity

Less key-person risk

An architecture chosen years ago because one developer preferred it becomes hard to understand for everyone who follows. CFA replaces a personal style with a documented, predictable layout: numbered layers, one folder per Feature, one composition root. The structure explains itself, so knowledge does not have to live in one person's head.

Peace of mind

For heads of department and owners

A formatted, readable, predictable layout makes the product easier to hand over, easier to review, and easier to staff. If the team changes, the next group opens the project, finds the map in AppModel.swift, and can see where to start. That is what keeps the company able to hire for this product for as long as it earns revenue.

Cost of adoption

Free, forever, and changeable

The CFA architecture and toolkit are published under the MIT licence. The README says: "You may use, copy, change and share the CFA architecture and CFA Toolkit, including in commercial work." There are no fees and no lock-in: a team can adopt it permanently and adapt it whenever its needs change.

github.com/3DaysOfSwift/cooperative-feature-architecture

One shared mental model

A model you can sketch, tests you can map

Because the Model is explicit (Features over services, under the ViewModels), a team can draw the app on a whiteboard and agree on it. The same drawing gives testing a format: ViewModel tests check how each ViewModel uses the Model, Feature tests check each part works as intended. Tests become easy to find, catalogue and organise, and a Feature without enough tests stands out as a thin row in the catalogue instead of an unnoticed gap.

Compounding value

Readable code is cheaper to change

Clear seams (a Feature behind a provider protocol, tests that await results) make it easier to review a change, to test it without the UI, and to hand it to a new colleague or an AI assistant with a precise place to start. This report did not time feature delivery; the point is that the conditions for faster, safer change are now in the code.

12. What's next: making it even more readable

The migration is a strong foundation. These remaining steps would finish the story:

  • More Features on @Observable. Today 3 of the 21 Features use it, and 42 ViewModel files do; moving the rest gives one standard way to expose state.
  • Consolidate state notification. ViewModel-to-view signalling currently uses closures (96 of 153 ViewModels) and Observation side by side; choosing one pattern per layer makes the codebase uniform.
  • Swift 6 language mode. The Xcode project still builds in Swift 5 mode; turning on Swift 6 lets the compiler enforce the isolation the code already documents.
  • Trim the remaining DispatchQueue calls. They went from 41 to 63 lines; the project-page controller alone has 23 call sites that re-dispatch to main, a leftover of the old observeForUI habit.
  • Tidy a few hand-written spots, such as the field count of 8 in SearchViewModel, and rename leftovers (test folders still called Library).
